# Первый пользовательский веб-интерфейс Spravoshnik EPB

## Цель

Добавить к существующему FastAPI-приложению первый пригодный для ежедневной работы
веб-интерфейс. После запуска адрес `/` должен открывать страницу входа или рабочую
область, а не возвращать 404. Первая версия охватывает вход, главную страницу и полный
базовый цикл работы с организациями.

## Границы первой версии

В первую версию входят:

- вход и выход с использованием существующих серверных сессий;
- общая оболочка: боковое меню, верхний поиск, профиль пользователя;
- главная страница с краткими показателями и быстрыми действиями;
- список организаций;
- поиск и фильтрация организаций по типу и активности;
- создание организации;
- просмотр карточки организации;
- редактирование основных сведений;
- просмотр и управление контактами и идентификаторами в рамках существующего API;
- понятные состояния загрузки, пустого списка, ошибки и запрета доступа;
- адаптация основных экранов для узкого окна.

Пункты будущих разделов показываются в меню как недоступные и помечаются «В разработке».
Их бизнес-функции в эту работу не входят.

## Визуальное направление

За основу принят предоставленный пользователем корпоративный образец:

- светлый рабочий фон;
- тёмная вертикальная навигация слева;
- компактная верхняя панель;
- плотные таблицы с ясной иерархией;
- синий как основной цвет и оранжевый для главного действия;
- спокойные нейтральные границы и поверхности;
- статусы дублируются текстом и цветом;
- русскоязычные подписи без смешения языков.

Интерфейс не зависит от внешних CDN: стили, сценарии и необходимые значки обслуживаются
самим приложением. Декоративные изображения пользователей не загружаются с внешних сайтов.

## Архитектура

Интерфейс реализуется внутри текущего FastAPI-монолита как серверные HTML-страницы.
Шаблоны отвечают за разметку, локальный CSS — за дизайн, небольшой локальный JavaScript —
за интерактивность форм и фильтров. Отдельное SPA и отдельный процесс сборки не вводятся.

Новый web-слой использует существующие сервисы и репозитории модулей identity и
organizations. Бизнес-правила не переносятся в HTML-маршруты и не дублируются в JavaScript.
API `/api/...` и Swagger `/api/docs` сохраняются без изменений.

Предлагаемое размещение:

```text
app/web/ui/
├── routes.py
├── dependencies.py
├── presenters.py
├── templates/
│   ├── base.html
│   ├── login.html
│   ├── dashboard.html
│   └── organizations/
└── static/
    ├── app.css
    └── app.js
```

## Маршруты

- `GET /` — перенаправление на `/login` или `/organizations` по состоянию сессии;
- `GET /login`, `POST /login` — форма входа;
- `POST /logout` — завершение сессии;
- `GET /dashboard` — первая главная страница;
- `GET /organizations` — список, поиск и фильтры;
- `GET /organizations/new`, `POST /organizations/new` — создание;
- `GET /organizations/{id}` — карточка;
- `GET /organizations/{id}/edit`, `POST /organizations/{id}/edit` — редактирование;
- отдельные POST-маршруты карточки — добавление и изменение контактов и идентификаторов.

Изменяющие запросы выполняются только методом POST и используют защиту от CSRF.

## Авторизация и поток данных

HTML-маршруты читают существующую HttpOnly session cookie и разрешают действия через те же
permissions, что и API. Неавторизованный пользователь перенаправляется на `/login`.
Недостаток permission возвращает страницу 403; скрытие кнопки служит только удобством и не
заменяет серверную проверку.

Форма проходит серверную валидацию. При ошибке она возвращается с сохранёнными безопасными
значениями и сообщением рядом с проблемным полем. После успешной записи используется схема
POST/Redirect/GET, чтобы обновление страницы не повторяло операцию.

## Состояния интерфейса

- неверные данные входа — единое сообщение без раскрытия существования пользователя;
- заблокированная учётная запись — существующая безопасная ошибка identity-модуля;
- пустой реестр — пояснение и кнопка создания при наличии права;
- 403 — понятная страница «Недостаточно прав»;
- 404 — страница «Объект не найден»;
- непредвиденная ошибка — нейтральное сообщение с request ID для диагностики;
- успешно выполненное действие — одноразовое уведомление после перенаправления.

## Тестирование и критерии готовности

Добавляются тесты HTML-маршрутов и сохраняются существующие API-тесты. Проверяются:

- `/` больше не возвращает 404;
- перенаправления гостя и вошедшего пользователя;
- успешный и неуспешный вход, выход;
- permission-проверки для просмотра и изменения организаций;
- вывод реальных организаций и безопасное экранирование текста;
- создание и редактирование с валидацией;
- поиск и фильтры;
- CSRF-защита изменяющих форм;
- страницы 403/404 и пустое состояние;
- отсутствие регрессий полного набора тестов.

Ручная проверка выполняется в браузере на широком и узком окне. Готовым считается результат,
в котором пользователь может войти, увидеть список, найти, создать, открыть и отредактировать
организацию без использования Swagger.

## Не входит в эту работу

- реализация договоров, экспертиз, задач, НПД и календаря;
- глобальный полнотекстовый поиск по будущим модулям;
- импорт и экспорт организаций;
- уведомления в реальном времени;
- отдельное мобильное приложение;
- смена существующей модели ролей, permissions или серверных сессий.
