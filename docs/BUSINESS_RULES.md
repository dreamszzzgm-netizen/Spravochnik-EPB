# BUSINESS_RULES.md — Spravoshnik EPB v1.2

## 1. Назначение

Документ фиксирует бизнес-правила, автоматические действия и допустимые переходы состояний.

---

# 2. Организации

1. Организация может быть юридическим лицом, ИП или филиалом.
2. Филиал может иметь ссылку на головную организацию.
3. Контактные лица принадлежат организации.
4. Один контакт может быть основным.
5. Старые значения реквизитов отдельно не версионируются.

---

# 3. ОПО

1. ОПО имеет владельца и эксплуатирующую организацию.
2. Они могут совпадать или быть разными.
3. ОПО может содержать технические устройства и здания/сооружения.
4. Техническое устройство и здание могут существовать без ОПО.
5. Удаление ОПО не должно физически удалять связанные технические устройства.

---

# 4. Технические устройства

1. Одна реальная единица создаётся один раз.
2. Устройство повторно используется в будущих договорах и экспертизах.
3. При создании желательно предупреждать о возможном дубле по организации + типу + заводскому номеру.
4. Контрольные даты оборудования создают уведомления.
5. По умолчанию контрольная дата оборудования не создаёт автоматическую задачу.

---

# 5. Здания и сооружения

1. Одна реальная единица создаётся один раз.
2. Может быть связана с ОПО или существовать без него.
3. Тип определяет набор дополнительных полей.

---

# 6. Договор

Статусы:

```text
Черновик
На согласовании
Подписан
В работе
Приостановлен
Завершён
Расторгнут
Архив
```

## 6.1. Переходы

Допустимые основные переходы:

```text
Черновик → На согласовании
На согласовании → Подписан
Подписан → В работе
В работе → Приостановлен
Приостановлен → В работе
В работе → Завершён
Подписан → Расторгнут
В работе → Расторгнут
Приостановлен → Расторгнут
Завершён → Архив
Расторгнут → Архив
```

## 6.2. Автоматический старт

Если договор `Подписан`, он автоматически переводится в `В работе` при первом фактическом начале работ:

- связанная workflow-задача переходит `Новая → В работе`; или
- связанная экспертиза выходит из `Подготовка` в следующий рабочий статус.

Само создание экспертизы в статусе `Подготовка` договор не запускает.

## 6.3. Приостановка

При переходе в `Приостановлен`:
- создаётся `ContractSuspension` с `started_at`, причиной и автором;
- одновременно допускается только один открытый период;
- связанные незавершённые задачи получают паузу расчёта срока;
- обычные уведомления о просрочке не создаются.

## 6.4. Возобновление

При `Приостановлен → В работе`:
- закрывается текущий `ContractSuspension` (`ended_at`);
- длительность паузы вычисляется по сохранённому периоду;
- сроки связанных незавершённых задач сдвигаются;
- уведомления пересчитываются;
- история периода сохраняется.

## 6.5. Расторжение

При расторжении:
- незавершённые связанные задачи отменяются;
- данные, документы и история сохраняются;
- экспертизы не удаляются.

## 6.6. Завершение

Автоматическое закрытие запрещено.

Система выполняет `readiness check`.

Минимальные условия:
- все связанные обязательные экспертизы завершены;
- все обязательные задачи выполнены или отменены;
- необходимые документы сформированы;
- заключения переданы заказчику.

Если условия выполнены:
```text
ready_to_complete = true
```

Пользователь с правом `contracts.change_status` вручную подтверждает завершение.

---

# 6.7. Дополнительные соглашения

1. Дополнительное соглашение относится ровно к одному договору.
2. Оно имеет собственный номер, дату, статус и документ.
3. Изменение суммы или срока договора применяется только после перехода соглашения в `Подписано`.
4. Дополнительное соглашение не перезаписывает исторические значения без следа: система должна позволять восстановить исходный договор и цепочку изменений.
5. Отменённое соглашение не влияет на действующую сумму/срок.
6. Действия с дополнительными соглашениями требуют `contracts.manage_addenda`.

---

# 7. Предмет договора

1. Один договор содержит один или несколько предметов.
2. Предмет содержит минимум один предмет экспертизы.
3. Один предмет может включать несколько технических устройств и/или зданий/сооружений.
4. Стоимость договора = сумма активных предметов договора.
5. Предмет не имеет собственного отдельного срока в v1.

---

# 8. Экспертиза

Главное правило:

> **1 экспертиза = 1 предмет экспертизы**

В v1:
- техническое устройство;
- здание/сооружение.

В будущем:
- документация.

Экспертиза создаётся вручную.

---

# 9. Связь экспертизы с договором

1. Экспертиза относится к одному договору.
2. Может быть связана с несколькими предметами этого же договора.
3. Запрещено связать экспертизу с предметом другого договора.
4. Предмет экспертизы должен входить хотя бы в один выбранный предмет договора.

---

# 10. Участники экспертизы

1. Ровно один ответственный эксперт.
2. Дополнительных экспертов может быть несколько.
3. Специалистов может быть несколько.
4. Эксперт может быть штатным или внешним.
5. Специалисты v1 — штатные.
6. Отсутствующий сотрудник не должен предлагаться для автоматического назначения.

---

# 11. Статусы экспертизы

```text
Подготовка
Сбор документов
Обследование
Подготовка заключения
Внутреннее согласование
Готово к регистрации
На рассмотрении в РТН
Отказ РТН / Требует доработки
Зарегистрировано
Получено заказчиком
Завершено
```

## 11.1. Основной поток

```text
Подготовка
→ Сбор документов
→ Обследование
→ Подготовка заключения
→ Внутреннее согласование
→ Готово к регистрации
→ На рассмотрении в РТН
→ Зарегистрировано
→ Получено заказчиком
→ Завершено
```

## 11.2. Отказ РТН

```text
На рассмотрении в РТН
→ Отказ РТН / Требует доработки
→ Готово к регистрации
→ новая попытка
```

## 11.3. Запрет прямого редактирования статуса

UI не должен записывать произвольную строку status.

Переход выполняется сервисом, который:
- проверяет текущий статус;
- проверяет право;
- проверяет обязательные условия;
- выполняет связанные действия;
- пишет audit.

---

# 12. Обследование

1. На экспертизу максимум одно основное обследование.
2. В нём хранятся диагностика, НК, дефекты, фотографии, результаты и материалы.
3. Рассмотренные документы выбираются из существующих документов.
4. Копии файлов не создаются.
5. Рассмотренные документы используются при формировании заключения.

---

# 13. Диагностика и НК

1. Методы берутся из справочника.
2. Можно вводить вручную.
3. Можно импортировать из Excel.
4. Результаты относятся только к конкретной экспертизе/обследованию.
5. Глобального реестра НК нет.

---

# 14. Дефекты

1. Дефект относится к обследованию.
2. Имеет описание, место, размер, критичность, фото, рекомендацию.
3. Глобального реестра дефектов нет.
4. Дефекты могут автоматически включаться в заключение.

---

# 15. Расчёты

1. Расчёт относится к экспертизе.
2. Хранятся исходные данные и методика.
3. Автоматический результат может быть изменён экспертом.
4. Если экспертный результат отличается, причина обязательна.
5. Экспертный результат имеет приоритет при формировании итогового заключения.
6. В v1 разрешена загрузка готового расчёта.

---

# 16. Заключение ЭПБ

Перед переводом к финальной подготовке система проверяет минимум:
- предмет экспертизы выбран;
- ответственный эксперт назначен;
- необходимые НПД выбраны;
- обследование заполнено, если требуется типом экспертизы;
- необходимые результаты внесены;
- расчёты присутствуют, если требуются;
- обязательные разделы заключения доступны.

ИИ не принимает окончательное экспертное решение.

---

# 17. Версии заключения

1. Пользователь видит одну текущую рабочую версию.
2. При существенном сохранении предыдущая может уходить в hidden backup.
3. Hidden backup можно восстановить.
4. Финальная версия не блокируется навсегда от исправления.
5. Изменения после финализации должны попадать в audit.

---

# 18. Регистрация ЭПБ в Ростехнадзоре

1. Экспертиза может иметь много попыток.
2. Номер попытки увеличивается последовательно.
3. Повторная подача = новая попытка.
4. История предыдущих попыток сохраняется.

Состояния попытки:

```text
Подготовлена
Направлена
На рассмотрении
Зарегистрирована
Отказ
```

---

## 18.1. Историческая неизменяемость попыток

После создания попытки №N+1 попытка №N считается исторической.

Обычное редактирование не может менять её бизнес-результат.

Исправление явной технической ошибки:
- отдельный permission;
- обязательная причина;
- audit;
- status history.

# 19. Создание пакета РТН

Перед созданием пакета:
- экспертиза должна быть `Готово к регистрации`;
- обязательные документы должны существовать;
- должны быть выполнены проверки комплектности.

После формирования:
- создаётся попытка `Подготовлена`;
- генерируется пакет документов.

После фактической отправки пользователь подтверждает:
```text
Подготовлена → Направлена
```

После этого:
```text
Экспертиза → На рассмотрении в РТН
```

---

# 20. Результат РТН

Если зарегистрировано:
- attempt → `Зарегистрирована`;
- обязательны номер реестра и дата регистрации;
- expertise → `Зарегистрировано`.

Если отказ:
- attempt → `Отказ`;
- решение/файл сохраняется;
- expertise → `Отказ РТН / Требует доработки`.

---

# 21. Передача заказчику

После фактической передачи зарегистрированного заключения пользователь вручную ставит:
```text
Зарегистрировано → Получено заказчиком
```

После выполнения финальных условий:
```text
Получено заказчиком → Завершено
```

---

# 22. Задачи

Статусы:
```text
Новая
В работе
Выполнена
Отменена
```

Просрочка:
```text
due_date < today
AND status not in (Выполнена, Отменена)
```

`Просрочена` не записывается как обычный статус.

---

# 23. Исполнители

1. У задачи может быть несколько исполнителей.
2. Назначение создаёт уведомление.
3. Личная задача может не иметь связанной бизнес-сущности.
4. Постановщик сохраняется отдельно.

---

# 24. Workflow

При создании экспертизы можно применить настроенный workflow template.

Автоматически создаются задачи.

Поля шаблона:
- название;
- роль исполнителя;
- относительный срок;
- приоритет;
- обязательность.

Следующая задача не блокируется предыдущей.

---

# 25. Сроки задач

1. Базово рассчитываются от сроков договора/события workflow.
2. Учитывается производственный календарь.
3. Изменение срока договора может вызывать пересчёт незавершённых задач.
4. Приостановка договора ставит срок на паузу.
5. Возобновление сдвигает даты.
6. Ручная корректировка задачи допускается по правам.

---

# 26. Уведомления

По умолчанию:
- 30 дней;
- 14 дней;
- 5 дней.

Дополнительно:
- назначение;
- просрочка;
- изменение статуса;
- @mention;
- контрольная дата.

Повторяющиеся уведомления должны использовать dedup, чтобы не создавать сотни одинаковых записей.

---

# 27. Документы

1. Физический файл хранится один раз на версию.
2. Логический документ может иметь несколько ссылок.
3. При загрузке новой редакции создаётся новая версия.
4. Удаление идёт через корзину.
5. Доступ проверяется backend.

---

# 28. Генерация документов

Если все необходимые данные и правила уже существуют:
- новый шаблон добавляется без кода.

Если нужны:
- новые данные;
- новые вычисления;
- новые бизнес-правила;
- новый алгоритм сборки,

требуется программное расширение builder/provider.

---

# 29. НПД

1. Экспертиза получает рекомендованный набор НПД.
2. Эксперт может добавить или исключить НПД.
3. Экспертиза фиксирует конкретные редакции НПД.
4. Новая редакция не перезаписывает старую.
5. Обновление НПД не меняет задним числом завершённую экспертизу.
6. Локальная база считается рабочим источником.
7. Интернет-проверка только предлагает изменение.
8. Критичное обновление статуса НПД требует подтверждения.

---

# 30. Импорт

Импорт всегда:

```text
upload
→ parse
→ normalize
→ validate
→ duplicate detection
→ preview
→ confirmation
→ transactional save
```

Без подтверждения рабочие записи не создаются.

---

# 31. Дубли

При потенциальном дубле:
- система предупреждает;
- пользователь выбирает действие;
- автоматическое молчаливое объединение запрещено.

---

# 32. Recognition / OCR

1. Recognition создаёт candidate data.
2. Поля с низкой уверенностью подсвечиваются.
3. Пользователь редактирует/подтверждает.
4. Только после подтверждения вызывается доменный сервис.
5. Массовое создание десятков объектов без подтверждения запрещено.

---

# 33. ИИ

1. ИИ предлагает, пользователь подтверждает.
2. Данные классифицируются минимум как `PUBLIC / INTERNAL / CONFIDENTIAL / PERSONAL`.
3. Внешний AI не получает запрещённые `PERSONAL` или `CONFIDENTIAL` данные.
4. Конфиденциальные документы — local AI only.
5. Администратор может запретить внешний AI.
6. Перед внешней отправкой показывается состав данных.
7. `extract/classify` используют schema-validated structured response.
8. Полные prompts/responses по умолчанию не сохраняются.

---

# 34. Права

Все критичные действия требуют permission backend.

UI-скрытие кнопки — только удобство, не защита.

---

# 35. Soft delete

При soft delete:
- запись исключается из обычных списков;
- связи не должны ломаться физически;
- восстановление возможно по праву;
- физическая очистка не является обычной операцией пользователя.

---

# 36. Audit

Audit создаётся для:
- входа;
- выхода;
- неудачного входа;
- создания;
- редактирования;
- удаления;
- восстановления;
- смены статуса;
- генерации ключевых документов;
- операций РТН;
- backup/restore.

---

# 37. Backup

Автоматически:
- раз в неделю;
- хранить последние 3 успешные копии.

Manual backup:
- разрешён администратору.

Restore:
- только администратору;
- с подтверждением;
- с проверкой совместимости;
- желательно с safety backup перед восстановлением.

---

# 38. Работа без интернета

Без внешнего интернета должны работать:
- организации;
- ОПО;
- устройства;
- здания;
- договоры;
- экспертизы;
- задачи;
- документы;
- генерация;
- НПД локально;
- календарь;
- backup;
- локальный AI.

Не работают только внешние функции:
- external AI;
- internet actuality check;
- будущая внешняя проверка реестров.

---


# 39. Файловые и внешние операции

1. PostgreSQL-транзакция не откатывает filesystem/OCR/AI/PDF side effects.
2. Side effects после commit выполняются через persistent outbox/job.
3. Scheduler только планирует, Worker исполняет.
4. Job должна быть повторяемой/идемпотентной в допустимых пределах.

# 40. Нумерация

1. Номер выдаётся атомарно в PostgreSQL.
2. Два параллельных запроса не получают одинаковый номер.
3. Выданный номер не переиспользуется молча.

# 41. История статусов

Contract, Expertise и RTN RegistrationAttempt имеют отдельную status history.

Audit её не заменяет.

# 42. Optimistic locking

Для Contract, Expertise, OPO, TechnicalDevice и Building обязательна проверка `version`.

При конфликте изменения другого пользователя не перезаписываются.


# 43. Сотрудники, бизнес-функции и роли доступа

1. `Employee` и `User` — разные сущности.
2. Профессиональная функция сотрудника (`expert`, `specialist`, `accountant`, `contract_responsible`) не является authorization-role.
3. Authorization-role назначается только пользователю через `user_role_assignments`.
4. Один пользователь может иметь несколько authorization-ролей.
5. Permission и scope проверяются совместно на backend.
6. Внешний эксперт в v1.2 создаётся как `Employee` с `employment_type = external_expert`; поэтому ответственный эксперт всегда ссылается на существующий `Employee`.
7. Аттестационные данные хранятся только в `expert_attestations`, а не дублируются в профиле сотрудника.

# 44. Пользовательские сессии

1. После успешного входа создаётся серверная сессия.
2. В хранилище сохраняется hash session token, исходный токен не журналируется.
3. Logout отзывает текущую сессию.
4. Блокировка пользователя и административный reset могут отзывать все активные сессии.
5. Таймаут бездействия проверяется сервером.
6. Cookie/session transport должен использовать безопасные настройки выбранного web-framework: HttpOnly, SameSite и Secure при HTTPS/VPN reverse proxy.
7. Смена или административный сброс пароля фиксируется audit-событием без записи пароля/секрета.

# 45. Workflow versions

1. Администратор редактирует логический workflow через создание новой версии.
2. Уже созданные задачи сохраняют ссылку на версию и task-template, из которых они были созданы.
3. Публикация новой версии workflow не изменяет существующие задачи.
4. Назначение исполнителя в шаблоне использует бизнес-функцию сотрудника, а не authorization-role.

# 46. PMLA и производственный контроль

1. ПМЛА относится к одному ОПО и содержит отдельные структурированные данные по опасным веществам, сценариям, ответственным и аварийным службам.
2. Генерируемый документ ПМЛА не является единственным источником этих данных.
3. Производственный контроль моделирует цепочку `план → проверка → нарушение → мероприятие`.
4. Мероприятие может существовать в плане без нарушения, но если связано с нарушением, оба объекта должны относиться к одному плану.
