# ARCHITECTURE.md — Spravoshnik EPB v1.2

## 1. Назначение

Этот документ фиксирует целевую архитектуру Spravoshnik EPB v1 и является следующим уровнем после функциональной спецификации в `README.md`.

Он определяет:

- архитектурный стиль;
- границы модулей;
- ответственность слоёв;
- правила зависимостей;
- хранение данных и файлов;
- генерацию документов;
- ИИ-контур;
- фоновые процессы;
- безопасность;
- резервное копирование;
- требования к многопользовательской работе;
- подход к расширяемости и тестированию.

Физическая схема БД будет описана отдельно в `DATA_MODEL.md`.

---

## 2. Архитектурные цели

Spravoshnik EPB должен быть:

1. **Модульным** — договоры, экспертизы, ОПО, документы и другие части не смешиваются в одном большом модуле.
2. **Расширяемым** — новые типы технических устройств, документов, НК и дополнительные поля по возможности добавляются без изменения ядра.
3. **Безопасным** — персональные и конфиденциальные данные остаются внутри организации, если нет явного разрешения на безопасную внешнюю обработку.
4. **Многопользовательским** — несколько сотрудников одновременно работают с одной серверной установкой по LAN.
5. **Тестируемым** — бизнес-правила проверяются отдельно от HTTP/UI.
6. **Надёжным** — критичные действия выполняются транзакционно.
7. **Аудируемым** — значимые действия пользователей фиксируются.
8. **Управляемым администратором** — справочники, шаблоны, workflow и часть полей меняются без участия разработчика.
9. **Подготовленным к развитию** — v1 не блокирует новые виды экспертиз, расчётов, документов и интеграций.

## 3. Предметные сущности

В архитектуре строго различаются:

- Организация;
- ОПО;
- Техническое устройство;
- Здание / сооружение;
- Договор;
- Предмет договора;
- Экспертиза;
- Предмет экспертизы;
- Обследование;
- Задача;
- Документ;
- НПД;
- Попытка регистрации ЭПБ в Ростехнадзоре;
- Учёт технического устройства в Ростехнадзоре;
- ПМЛА;
- Производственный контроль;
- Сотрудник;
- Пользователь.

### Терминологическое правило

Универсальная пользовательская сущность с названием `Объект` не используется.

Пользователь работает с:

- ОПО;
- техническими устройствами;
- зданиями и сооружениями.

`Предмет экспертизы` — логическая ссылка на то, что проходит экспертизу.

В v1 это:

- техническое устройство;
- здание/сооружение.

Архитектура должна позволять позднее добавить документацию и другие допустимые виды предмета экспертизы.

## 4. Ключевые бизнес-инварианты

1. ОПО, техническое устройство и здание/сооружение — разные сущности.
2. Техническое устройство создаётся как постоянная карточка один раз.
3. Здание/сооружение создаётся как постоянная карточка один раз.
4. Техническое устройство может существовать без ОПО.
5. Здание/сооружение может существовать без ОПО.
6. ОПО может иметь отдельного владельца и отдельную эксплуатирующую организацию.
7. Один договор содержит один или несколько предметов договора.
8. Один предмет договора связан минимум с одним предметом экспертизы.
9. **Одна экспертиза относится ровно к одному предмету экспертизы.**
10. Экспертиза может быть связана с несколькими предметами одного договора, если это требуется бизнес-процессом.
11. Экспертиза создаётся вручную.
12. Статус рассмотрения в РТН относится к экспертизе/регистрационной попытке, а не к договору.
13. Одна экспертиза может иметь несколько попыток регистрации в РТН.
14. Повторная подача — новая регистрационная попытка.
15. Просроченность задачи — вычисляемое состояние, а не основной статус.
16. Один физический документ не дублируется из-за нескольких связей.
17. Договор завершается только после системной проверки и ручного подтверждения.
18. Новый шаблонный документ по существующим данным не должен требовать изменения кода.
19. Новая бизнес-логика, вычисления или источники данных могут требовать изменения кода.
20. Персональные данные не передаются внешнему ИИ без разрешённой безопасной обработки.
21. ИИ не сохраняет критичные изменения без подтверждения пользователя.
22. Важные сущности удаляются логически через корзину.
23. Критичные операции подчиняются системе прав доступа.

## 5. Архитектурный стиль

Для v1 используется **модульный монолит с чётким сервисным слоем**.

```text
Пользовательский интерфейс
        ↓
HTTP / Presentation Layer
        ↓
Application / Service Layer
        ↓
Domain Rules
        ↓
Persistence / Repositories
        ↓
PostgreSQL
```

Параллельно бизнес-сервисы работают с инфраструктурой:

```text
Бизнес-сервисы
   ├── Файловое хранилище
   ├── Генератор документов
   ├── Import / OCR
   ├── AI Gateway
   ├── Уведомления
   ├── Планировщик
   └── Backup
```

### Почему не микросервисы

Для v1 микросервисы не нужны, потому что:

- система устанавливается внутри одной организации;
- требуется локальная эксплуатация;
- бизнес-операции тесно связаны;
- важны простые транзакции между договорами, экспертизами, задачами и документами;
- микросервисы усложнят установку, поддержку, backup и диагностику.

При этом модули должны иметь чёткие границы, чтобы при будущем росте отдельный сервис можно было выделить без переписывания всей системы.

## 6. Слои приложения

### 6.1 Presentation Layer

Отвечает за:

- HTTP-запросы;
- маршруты;
- формы;
- сериализацию;
- отображение;
- базовую проверку формата входных данных;
- передачу команды в application/service layer.

Сложная бизнес-логика в routes запрещена.

### 6.2 Application / Service Layer

Координирует пользовательские сценарии:

- создание договора;
- добавление предмета;
- создание экспертизы;
- назначение экспертов;
- смену статусов;
- завершение договора;
- создание workflow-задач;
- регистрацию попытки подачи в РТН;
- импорт;
- генерацию документов;
- уведомления.

### 6.3 Domain Layer

Содержит бизнес-правила, не зависящие от UI или HTTP:

- допустимые переходы статусов;
- условия завершения договора;
- правила повторной подачи;
- расчёт просрочки;
- пересчёт сроков после приостановки;
- `1 экспертиза = 1 предмет экспертизы`;
- проверки перед финализацией заключения;
- правила применимости НПД.

### 6.4 Persistence Layer

Отвечает за:

- чтение;
- сохранение;
- запросы;
- транзакции;
- soft delete;
- индексы;
- конкурентный доступ.

HTTP-слой не должен выполнять SQL напрямую.

### 6.5 Infrastructure Layer

Содержит технические реализации:

- файловая система;
- DOCX/PDF;
- Excel;
- OCR;
- локальный AI;
- внешние AI API;
- backup;
- scheduler;
- производственный календарь;
- интеграции.

Доменные правила не должны зависеть от конкретной DOCX-библиотеки, OCR-движка или AI-провайдера.

## 12. Contracts

Отвечает за:

- стоимость;

- ответственных;

### Статусы договора

```text
Черновик
На согласовании
Подписан
В работе
Приостановлен
Завершён
Расторгнут
Архив
```

### Завершение

`ContractCompletionService` проверяет минимум:

- все необходимые экспертизы завершены;
- незавершённых обязательных задач нет;
- необходимые документы сформированы;
- заключения переданы заказчику.

Сервис возвращает готовность и список блокирующих причин.

Фактический переход в `Завершён` выполняется только после команды пользователя.

## 13. Expertises

Отвечает за:

- карточку экспертизы;
- договор;
- связь с предметами договора;
- один предмет экспертизы;
- тип экспертизы;
- ответственного эксперта;
- дополнительных экспертов;
- специалистов;
- статус;
- заключение;
- обследование;
- НПД;
- попытки регистрации в РТН.

### Предмет экспертизы

В доменной модели должна существовать абстракция `ExpertiseSubjectRef`.

В v1:

```text
TECHNICAL_DEVICE + id
BUILDING + id
```

В будущем:

```text
DOCUMENTATION + id
```

Главный инвариант:

```text
Expertise → exactly one ExpertiseSubjectRef
```

### Статусы экспертизы

```text
Подготовка
Сбор документов
Обследование
Подготовка заключения
Внутреннее согласование
Готово к регистрации
На рассмотрении в РТН
Отказ РТН / Требует доработки
Зарегистрировано
Получено заказчиком
Завершено
```

Переходы выполняются через отдельный сервис статусов, а не прямой записью поля из UI.

## 14. Inspections

На одну экспертизу — максимум одно основное обследование.

```text
Inspection
├── Diagnostics
├── NDT results
├── Defects
├── Photos
├── Results
├── Materials
└── Reviewed documents
```

Диагностика, НК и дефекты не являются глобальными пользовательскими модулями.

Но в БД они могут храниться в структурированных внутренних таблицах, например:

```text
inspection_ndt_results
inspection_defects
inspection_photos
```

То есть структурированные данные — да, глобальные реестры — нет.

## 15. Calculations

- вид расчёта;

## 16. Rostechnadzor

Модуль разделяет два независимых процесса.

### 16.1 Учёт технического устройства

Связан с техническим устройством.

Храним:

- учётный номер;
- дату;
- основание;
- заявление;
- акт готовности;
- решение;
- документы.

### 16.2 Регистрация заключения ЭПБ

Связана с экспертизой.

```text

```

Для попытки:

- порядковый номер;
- дата подготовки;
- дата направления;
- состояние;
- результат;
- номер реестра;
- дата регистрации;
- решение РТН;
- документы.

Состояния:

```text
Подготовлена
Направлена
На рассмотрении
Зарегистрирована
Отказ
```

Повторная подача создаёт новую попытку.

## 17. Tasks

Задача — универсальная рабочая единица.

Может быть связана с:

- организацией;
- договором;
- предметом договора;
- техническим устройством;

Также допускается личная задача без бизнес-сущности.

Статусы:

```text
is_overdue

```

## 18. Workflow

Шаблоны рабочих процессов не кодируются жёстко в routes.

Администратор задаёт логический шаблон и публикуемые версии.

Для каждой версии задаются:

- название шаблона;
- область применения;
- задачи;
- бизнес-функция исполнителя (не authorization-role);
- относительный срок;
- приоритет;
- порядок;
- обязательность.

Пример:

```text
Экспертиза создана
↓
WorkflowTemplateVersion
↓
Набор Task с ссылкой на source version/template item
```

---

## 19. Documents

Документ — универсальная сущность.

Файл физически хранится один раз и может иметь несколько связей:

```text
Document
├── Organization
├── OPO
├── TechnicalDevice
├── Building
├── Contract
├── Expertise
└── Task
```

### Хранение

В БД хранится метаинформация.

Файлы хранятся в локальном серверном файловом хранилище.

Крупные бинарные файлы не должны быть основным содержимым БД без специальной причины.

### Имена файлов

Внутреннее физическое имя должно использовать уникальный идентификатор, а исходное пользовательское имя хранится как метаданные.

Это снижает риск конфликтов, path traversal и непреднамеренной перезаписи.

---

## 20. Версии документов

Обычный документ:

```text
Document
  ├── DocumentVersion 1
  ├── DocumentVersion 2
  └── DocumentVersion 3
```

Связи с бизнес-карточками относятся к логическому документу.

Для заключения ЭПБ пользователь видит одну текущую редакцию, а предыдущие редакции могут храниться как скрытые резервные версии с возможностью восстановления.

## 21. DocumentGeneration

Генерация отделена от обычного файлового хранилища.

### Простая генерация

```text
Context Data
↓
Template
↓
DOCX
↓
optional PDF
```

### Сложная генерация

```text
Context Data
↓
Document Builder
↓
Business Rules
↓
Calculations / AI / Tables
↓
Prepared Context
↓
Template Renderer
↓
DOCX
↓
PDF
```

Компоненты:

- `TemplateRegistry`;
- `TemplateRenderer`;
- `DocumentContextBuilder`;
- `DocumentGenerator`;
- `PdfConverter`;
- специализированные `DocumentBuilder`.

Примеры:

```text
ExpertiseConclusionBuilder
PMLABuilder
ProductionControlReportBuilder
RTNApplicationBuilder
```

## 22. Шаблоны документов

Шаблон содержит:

- тип документа;
- название;
- DOCX-файл;
- область применения;
- активность;
- версию;
- правила выбора;
- используемые переменные.

Новая форма не требует изменения кода, если:

- нужные данные уже существуют;
- нужные вычисления уже существуют;
- контекст шаблона умеет предоставить значения.

Если нужна новая бизнес-логика — добавляется builder/provider, но общий механизм шаблонов не меняется.

## 23. NormativeDocuments

Локальная нормативная база хранит:

- документ;
- тип;
- номер;
- название;
- орган;
- даты;
- статус;
- источник;
- локальный файл;
- связи с типами предметов экспертизы;
- связи с типами экспертизы.

Экспертиза получает рекомендованный набор НПД, который эксперт может корректировать.

## 25. PMLA

ПМЛА относится к конкретному ОПО.

```text
OPO 1 → N PMLA
```

Поддерживаются:

- периоды;
- версии;
- данные ОПО;
- состав оборудования;
- здания/сооружения;
- структурированные опасные вещества;
- структурированные сценарии аварий;
- ответственные сотрудники;
- аварийные службы;
- DOCX/PDF.

Генерируемый файл не является единственным источником данных ПМЛА: перечисленные сведения хранятся структурированно и используются генератором документов.

## 26. ProductionControl

Не обязан быть глобальным пунктом меню, но остаётся отдельным бизнес-модулем.

Хранит связанную цепочку:

```text
Plan
↓
Inspection
↓
Violation
↓
Corrective Action
```

Также мероприятие может относиться непосредственно к плану без нарушения.

Храним сроки, ответственных, статусы и результаты. Generic `item_type` не используется как единственная модель этих сущностей.

Используется для формирования:

- годового плана;
- отчёта;
- положений;
- приказов;
- инструкций;
- других документов.

## 27. Employees

Отвечает за:

- сотрудников;
- роли;
- контактные данные;
- присутствие;
- отпуск;
- больничный;
- штатный/внешний статус;
- экспертные атрибуты.

Сотрудник и пользователь — разные сущности.

Не каждый сотрудник обязан иметь учётную запись.

Профессиональные функции сотрудника (эксперт, специалист, бухгалтер, ответственный по договору и т. п.) отделены от authorization-ролей пользователя. Функция сотрудника используется в workflow и назначениях, но сама по себе не выдаёт permission.

Отсутствия сотрудника хранятся отдельными периодами (`EmployeeAbsence`), чтобы сохранять историю отпусков/больничных и корректно вычислять текущую доступность.

## 28. UsersAndPermissions

Отвечает за:

- аутентификацию;
- логины;
- пароли;
- блокировку;
- сессии;
- суперпользователя;
- роли;
- разрешения;
- смену пароля;
- сброс пароля администратором.

### Backend-проверка обязательна

Скрытая кнопка в UI не является защитой.

Требуется одновременно:

```text
UI: действие скрыто/запрещено
+
Backend: permission check
```

### Permission-based модель

Рекомендуется строить права не только по ролям, но и по разрешениям:

```text
contracts.view
contracts.create
contracts.change_status
expertises.view
expertises.edit
expertises.register_rtn
documents.generate
settings.manage
users.manage
```

Роль — набор разрешений.

Назначение роли хранится явно как `UserRoleAssignment`:

```text
User
↓
UserRoleAssignment
├── Role
├── Scope (ALL / ASSIGNED / RELATED / OWN)
└── optional scope_config
```

Профессиональная функция Employee не является Role доступа.

Сессии серверные и отзывные. В хранилище сохраняется hash session token; блокировка пользователя, logout и административный revoke должны прекращать действие соответствующих сессий.

Полная матрица описана в `PERMISSIONS.md`.

## 35. AI Architecture

ИИ абстрагируется через общий интерфейс:

```text
AIService
├── LocalAIProvider
├── OllamaProvider
├── ExternalAIProvider
└── FutureProvider
```

Бизнес-код не обращается напрямую к конкретному API.

### AI Gateway

Все AI-вызовы проходят через единый шлюз:

```text
Feature
↓
AIGateway
├── Policy Check
├── Data Classification
├── PII Sanitizer
├── Local/External Routing
├── Provider Adapter
└── Response Validation
```

### Локальный ИИ

Может получать персональные и конфиденциальные данные только при реальной локальной обработке без передачи наружу.

### Внешний ИИ

Обязательная цепочка:

```text
Data
↓
PII detection
↓
sanitation / pseudonymization
↓
preview
↓
user confirmation
↓
external provider
```

Администратор может полностью отключить внешний ИИ.

### Хранение AI-данных

Полные внешние prompts/responses по умолчанию не сохраняются.

Можно сохранять безопасные технические метаданные:

- тип операции;
- провайдер;
- время;
- success/failure;
- код ошибки.

## 39. База данных

Для целевой многопользовательской версии рекомендуется **PostgreSQL**.

Причины:

- параллельная работа;
- транзакции;
- ограничения;
- индексы;
- mature backup;
- поддержка JSONB для контролируемых dynamic fields;
- хорошая поддержка Python.

SQLite допустим для прототипов и части тестов, но не как основная рабочая БД LAN-версии.

---

## 40. Динамические поля

Нельзя превращать всю предметную модель в бесконтрольный JSON.

Подход:

```text
Core fields → обычные колонки
Custom field definitions → отдельные определения
Custom values → контролируемые значения
```

JSONB допустим как часть технической реализации, если:

- поле заранее описано;
- тип проверяется;
- обязательность проверяется;
- единицы измерения известны;
- данные можно корректно искать и экспортировать.

Точная модель будет в `DATA_MODEL.md`.

---

## 41. Транзакции

Многошаговые критичные операции выполняются атомарно.

### Создание экспертизы

```text
Create Expertise
+ assign subject
+ assign participants
+ link contract subjects
+ create workflow tasks
+ audit
```

Ошибка обязательного шага откатывает всю операцию.

### Расторжение договора

```text
Change contract status
+ cancel unfinished tasks
+ audit
```

Также единая транзакция.

---

## 42. Конкурентная работа

Несколько пользователей могут одновременно редактировать данные.

Минимальные средства защиты:

- `updated_at`;
- транзакции;
- уникальные ограничения;
- проверка актуальности перед критическим сохранением.

Для важных карточек рекомендуется optimistic locking через `version` или эквивалентную проверку.

Второй пользователь не должен молча затереть изменения первого.

---

## 43. Файловое хранилище

Файлы хранятся локально на сервере организации.

Физическая структура не обязана повторять пользовательскую.

Пример:

```text
storage/
  files/
    <uuid>
  versions/
    <uuid>
  templates/
  generated/
  temp/
```

Пользователь работает через карточки системы и не зависит от физической структуры каталогов.

---

## 44. Безопасность файлов

При загрузке:

- ограничивать размер;
- очищать пользовательское имя;
- запрещать path traversal;
- не использовать исходное имя как физический путь;
- проверять MIME/тип;
- при необходимости хранить checksum;
- проверять permissions при скачивании.

Приватное файловое хранилище не раздаётся как открытая static-папка.

## 71. Решения, принятые в Architecture v1.2

1. Архитектура — модульный монолит.
2. Целевая БД — PostgreSQL.
3. Файлы хранятся отдельно от БД в локальном серверном storage.
4. Клиенты работают через браузер по LAN.
5. Удалённый доступ — через VPN/защищённую сеть.
6. Бизнес-логика не размещается в HTTP routes.
7. Схема БД изменяется через миграции.
8. Документы и генерация документов — разные подсистемы.
9. ИИ вызывается только через единый AI Gateway.
10. Импорт всегда проходит preview/validation/confirmation.
11. OCR/Recognition не пишет рабочие данные напрямую.
12. Permissions проверяются на backend.
13. Soft delete используется для важных сущностей.
14. Audit и технические logs разделены.
15. Scheduler — серверный компонент.
16. Основной функционал работает без внешнего интернета.
17. Микросервисы для v1 не используются.

# 74.1. Архитектурные уточнения v1.2 после review

## 74.1.1. Audit и Status History

`Audit` отвечает на вопрос «кто и что сделал».

`Status History` отвечает на вопрос «как сущность проходила бизнес-процесс».

Отдельная история статусов обязательна минимум для:
- Contract;
- Expertise;
- RTN RegistrationAttempt.

## 74.1.2. Периоды приостановки договора

Приостановки хранятся отдельными периодами:

```text
ContractSuspension
├── contract_id
├── started_at
├── ended_at NULL
├── reason NULL
└── created_by
```

Это позволяет воспроизводимо объяснить пересчёт сроков.

## 74.1.3. Optimistic locking

`version` обязателен минимум для:
- Contract;
- Expertise;
- OPO;
- TechnicalDevice;
- Building.

Молчаливое перезаписывание чужих изменений запрещено.

## 74.1.4. StoredFile

Разделяются:

```text
Document        — логический документ
DocumentVersion — редакция
StoredFile      — физический бинарный файл
```

`StoredFile` хранит:

```text
storage_key
sha256
size_bytes
mime_type
created_at
```

SHA-256 обязателен.

## 74.1.5. DB transaction и внешние side effects

Filesystem, OCR, AI, PDF и другие внешние операции не являются частью PostgreSQL-транзакции.

Правило:

```text
DB transaction
→ commit
→ persistent outbox/job
→ worker
→ сохранение результата
```

## 74.1.6. Scheduler и Worker

`Scheduler` определяет **когда**.

`Worker/Job Executor` выполняет **что**.

Job хранит минимум:

```text
job_key
job_type
status
attempt_count
scheduled_at
started_at
finished_at
last_error
```

## 74.1.7. Persistent Outbox

Синхронные domain events допустимы внутри бизнес-транзакции.

Ненадёжные side effects после commit публикуются через persistent outbox. Message broker в v1 не обязателен.

## 74.1.8. Permission + Scope

Permission отвечает «что разрешено», scope — «над какими данными».

```text
Permission: expertises.edit
Scope: ALL | ASSIGNED | RELATED | OWN
```

## 74.1.9. Атомарная нумерация

`NumberingService` выдаёт номера атомарно в PostgreSQL.

Параллельные запросы не могут получить одинаковый номер в одной области нумерации.

## 74.1.10. Версия workflow

Созданные задачи сохраняют ссылку/идентификатор версии workflow, из которой они были инстанцированы.

Изменение шаблона не меняет происхождение уже созданных задач.

## 74.1.11. TemplateContextSchema

Переменные DOCX-шаблонов являются стабильным публичным контрактом:

```text
organization.full_name
opo.registration_number
technical_device.serial_number
expertise.internal_number
```

Схема контекста версионируется.

## 74.1.12. Dynamic field_key

У каждого динамического поля есть неизменяемый системный `field_key`, отдельный от редактируемого названия.

## 74.1.13. Классификация данных для AI

Минимум:

```text
PUBLIC
INTERNAL
CONFIDENTIAL
PERSONAL
```

Внешняя отправка определяется не только наличием ПД, но и классом конфиденциальности.

## 74.1.14. Типы AI-операций

Минимум:

```text
draft
extract
classify
search
```

Для `extract` и `classify` обязателен schema-validated structured response.

## 74.1.15. Recognition confidence

Confidence хранится по каждому полю.

## 74.1.16. ImportSession

Импорт фиксирует:

```text
ImportSession
→ ImportRowResult[]
→ validation
→ duplicate candidates
→ user decision
→ final result
```

Стратегия поиска дублей определяется отдельно для каждой сущности.

## 74.1.17. Data conventions

```text
бизнес-дата    → PostgreSQL DATE
момент события → PostgreSQL TIMESTAMPTZ
деньги         → NUMERIC + currency
```

Naive datetime и `float` для денег запрещены.

## 74.1.18. FK delete policy

Для исторически значимых бизнес-данных запрещён необдуманный `ON DELETE CASCADE`.

По умолчанию:
- RESTRICT;
- SET NULL только при допустимом бизнес-смысле;
- soft delete.

## 74.1.19. GlobalSearchService

Глобальный поиск — отдельная application/read-model подсистема.

## 74.1.20. Expert Attestations

Удостоверения и области аттестации моделируются отдельными сущностями с периодами действия и документами.

## 74.1.21. RTN attempt immutability

После создания новой попытки предыдущая является исторической.

Изменение её бизнес-результата допускается только как исправление технической ошибки с отдельным permission, причиной и audit.

## 74.1.22. Generated document provenance

Для сгенерированного документа фиксируются:

```text
template_version
generator_version
context_schema_version
context_hash / snapshot metadata
generated_at
generated_by
```

## 74.1.23. Версионирование НПД

НПД хранит редакции.

Экспертиза связывается с конкретной редакцией. Обновление нормативной базы не изменяет задним числом завершённую экспертизу.

## 74.1.24. Backup verification

После backup проверяются:
- успешность `pg_dump`;
- manifest;
- checksums.

Должна существовать периодическая тестовая процедура восстановления.

## 74.1.25. Health checks

Состояния:

```text
OK
WARNING
ERROR
UNKNOWN
```

отдельно по БД, storage, backup, scheduler/worker, AI и другим подсистемам.

## 74.1.26. Correlation ID

`correlation_id/request_id` проходит через:

```text
HTTP → service → job/outbox → audit → technical log
```

## 74.1.27. File security

Проверяются:
- extension;
- detected MIME/signature;
- размер;
- разрешённый тип.

Клиентскому Content-Type не доверяем.

Предусматривается интерфейс `FileSecurityScanner`.

## 74.1.28. PostgreSQL integration tests

Бизнес-критичные repository/integration тесты выполняются на PostgreSQL.

SQLite не считается эквивалентной заменой для JSONB, constraints, locking и транзакционного поведения.

## 74.2. Решения review v1.2

### 74.2.1. Authorization и функции сотрудников

`EmployeeFunctionRole` и authorization `Role` — разные справочники. `UserRoleAssignment` связывает пользователя с ролью и scope. Это исключает автоматическую выдачу прав только потому, что сотрудник является экспертом или бухгалтером.

### 74.2.2. FK-backed business links

Задачи, комментарии и применимость НПД используют реальные FK link-таблицы для поддерживаемых типов. Generic `entity_type + entity_id` допустим только для технических метаданных, где осознанно принимается отсутствие FK и есть integrity policy.

### 74.2.3. Дополнительные соглашения

Дополнительное соглашение — отдельная сущность договора с собственным статусом, датой и документом. Подписанное соглашение может менять сумму/срок, но история исходного договора сохраняется.

### 74.2.4. Sessions

Серверные сессии имеют срок жизни, last activity и revoke. В хранилище не сохраняется исходный bearer/session token.

### 74.2.5. Workflow revisions

Редактирование workflow создаёт новую версию. Существующие задачи продолжают ссылаться на конкретную исходную версию.

### 74.2.6. Structured PMLA and Production Control

PMLA и ProductionControl имеют структурированные подмодели, а не только итоговые документы/универсальные items.
